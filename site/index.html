Linux · C · PCI · networking

A small Linux Ethernet driver, built to understand what happens between the kernel and a network card.

XNIC controls an emulated Intel 82540EM-compatible network device in QEMU. It sends and receives real packets, handles interrupts, and recovers from resets while traffic is running.

View the source Read the test report

This is an educational driver validated with an emulated device. It is not a claim of physical-silicon or production-driver experience.

What is happening here?

QEMU pretends to be a PCI Ethernet card. Linux discovers that card and loads XNIC. The driver then programs device registers and shares packet buffers with the device through DMA descriptor rings.

Linux networkingcreates and consumes packets
↔
XNIC driverowns lifecycle and synchronization
↔
DMA ringsdescribe packet memory
↔
QEMU NICemulates the hardware

On transmit, Linux gives the driver a packet. XNIC maps its memory for the device, writes a descriptor, and rings a register “doorbell.” On receive, an interrupt schedules NAPI so Linux can process packets in batches without being overwhelmed by interrupts.

What I implemented

  • Device setup: PCI discovery, BAR0 register mapping, reset, MAC-address discovery, and clean removal.
  • Packet movement: one transmit ring and one receive ring with DMA buffer ownership.
  • Traffic handling: interrupts, NAPI receive polling, queue stop/wake, and completion cleanup.
  • Recovery: serialized timeout and reset handling while traffic or teardown is in progress.
  • Visibility: ethtool counters, tracepoints, fault injection, raw logs, and packet captures.
  • DPDK: a separate one-port L2 forwarder validated with a virtual PCAP PMD.

One bug I can explain

A stalled 64-entry transmit ring stopped the Linux queue, but the diagnostic counter did not always show that the ring had become full. I first suspected completion timing. The real problem was that “full” was detected only on a future transmit call—after Linux had already honored the queue stop and might never call again.

The fix was to detect the transition immediately after consuming the last usable descriptor, under the same lock used by completion cleanup. The reproducer, rejected hypothesis, root cause, synchronization reasoning, and regression test are recorded in the bug diary.

What this proves—and what it does not

Evidence this project provides

  • Hands-on Linux PCI and netdev driver work in C
  • DMA descriptor ownership and memory ordering
  • Interrupt/NAPI and teardown synchronization
  • Repeatable debugging and fault-path testing
  • Functional DPDK and packet-capture experience

Experience it does not replace

  • Physical board or new-silicon bring-up
  • Oscilloscope, logic-analyzer, or JTAG work
  • Production or upstream driver ownership
  • Real-NIC DPDK performance validation
  • RDMA development or validation
